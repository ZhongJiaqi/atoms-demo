| 关注点 | 本项目的回答 |
| --- | --- |
| 做了什么 | 自然语言生成 React + Vite 项目，在受控沙盒中构建，以 SSE 展示真实执行过程，再在 iframe 中提供可交互预览；后续对话继续修改原项目 |

## 1. 实现思路与关键取舍

### 1.1 对产品核心体验的理解

本项目把核心体验收敛为：**描述需求 → 生成源码 → 构建验证 → 真实预览 → 在原项目上继续修改**。

首页与工作区参考 Atoms 的布局和交互，但实现目标不是复制其全部产品能力。相较于增加更多展示性入口，优先保证生成结果能操作、代码能恢复、修改沿用同一个项目，以及失败时给出真实反馈。

| 能力 | 当前做法 | 取舍原因 |
| --- | --- | --- |
| 智能体执行 | 单一 Coding Agent 驱动明确的生成、校验、构建和修复流程 | 先控制状态与失败边界，不引入多角色自由对话或多模型择优体系 |
| 应用生成 | 输出受控 React + TypeScript 多文件项目，使用固定 Vite 模板 | 接近真实前端工程，同时限制依赖和执行范围 |
| 预览 | 成功构建后展示真实页面，不把不完整的生成代码当作成功应用 | 避免模型输出未完成时出现不可运行的半成品 |
| 对话修改 | 读取已有源码，要求模型返回增量修改，并在同一项目下重新构建 | 保留已有功能与版本，减少每轮重建新项目造成的状态断裂 |
| 历史恢复 | 恢复保存的项目和版本；回滚旧代码时创建新版本 | 保留对话和历史，不破坏性覆盖已有成功记录 |
| 项目封面 | 使用统一静态 UI 卡面 | 不为首页展示额外启动截图沙盒，减少等待、资源消耗和外部依赖 |
| 应用业务数据 | 主要使用生成应用自身 Origin 的 localStorage | 当前聚焦小规模 Demo，不扩展到多用户后端数据平台 |

### 1.2 REA 调研如何进入实现

前期使用 **REA（reverse-engineer-anything）**，只分析有权限访问的页面，范围限定在首页视觉、Agent 工作区、首次生成流程和多轮修改流程。

调研产出为 [UI_SPEC.md](UI_SPEC.md) 和 [INTERACTION_SPEC.md](INTERACTION_SPEC.md)，区分直接观察、推测、实现建议与未知项。截图与界面证据用于决定布局、状态展示和交互顺序，不据此推断原产品内部架构。

因此，REA 在这里承担产品调研与规格提炼的作用；运行时的模型调用、项目持久化、沙盒和预览系统均由本项目实现。Codex 用于开发协作，不是用户生成应用时调用的运行时服务。

### 1.3 总体架构

| 层级 | 主要技术 | 责任 |
| --- | --- | --- |
| 宿主界面 | Next.js 15、React 19、TypeScript、Tailwind CSS 4 | 首页、认证、聊天工作区、源码查看和 iframe 容器 |
| 生成 API | Next.js Route Handlers、SSE | 验证用户与项目权限，接收需求并实时返回执行事件 |
| Coding Agent | Node.js、OpenAI SDK、OpenAI-compatible API | 生成文件、应用增量修改、校验输出、读取日志并修复；当前对接 DashScope |
| 生成应用 | React、TypeScript、Vite 6 | 在固定模板与受控依赖下构建浏览器应用 |
| 持久化 | Supabase Auth、Postgres / RLS、私有 Storage | 保存用户会话、项目、消息、源码、成功版本与构建产物 |
| 构建运行 | 本地 macOS sandbox-exec；线上 Vercel Sandbox | 隔离文件与执行范围，控制资源和运行时间 |
| 线上预览 | 独立项目 Origin、签名授权、Next.js 网关、sandboxed iframe | 读取私有静态产物，隔离宿主与生成应用 |

```text
用户需求
   │
   ▼
Next.js 工作区 / POST /api/generate
   ├─ Supabase 会话与项目访问校验
   └─ SSE：模型、文件、构建、修复、保存与预览状态
   │
   ▼
Coding Agent → React + Vite 源码 → 隔离 Sandbox 构建
   │                                      │
   │                           构建失败 → 日志修复（最多两轮）
   ▼
Supabase Postgres：成功项目快照
Supabase 私有 Storage：构建产物
   │
   ▼
签名预览网关 → 项目独立 Origin → iframe 可交互页面
```

关键入口可从 [生成 API](../app/api/generate/route.ts)、[本地生成状态机](../lib/agent/run-generation.ts) 和 [云端适配](../lib/agent/run-cloud-generation.ts) 开始阅读。

### 1.4 一次生成与后续修改的执行过程

1. 服务端验证用户会话、需求输入和项目访问权限。首次创建获得新项目 ID；修改请求携带原项目 ID。
2. 首次调用模型生成项目文件；修改时读取当前保存的源码，再生成增量修改。
3. 校验文件路径与结构，将文件写入当前任务的独立目录。模板、入口和依赖由平台控制，不交给模型任意改写。
4. 在受控环境中运行 TypeScript 检查和 Vite 构建。失败时把真实日志反馈给模型，最多修复两轮。
5. 构建通过后保存成功版本。云端先保存私有产物，再提交项目快照；临时目录不是永久存储。
6. 创建或恢复预览授权，前端更新 iframe。保存与预览是两个状态：源码已保存但预览尚未就绪时，会保留项目并显示可重试的反馈，而不是冒称全部成功。

SSE 承载真实阶段事件，不是固定进度动画。它适合当前服务端到浏览器的单向进度反馈；本项目尚未实现持久化事件回放，不把刷新恢复已完成项目描述为正在执行任务的可靠续跑。

### 1.5 为什么线上构建和预览分离

Vercel Function 不适合长期托管每个生成项目的 Vite 服务。本项目让 Vercel Sandbox 负责短时隔离构建，成功产物进入私有 Storage，再通过 Next.js 网关展示。

当前线上方案是**私有产物 + 预览网关 + 项目独立域名别名**，不是每轮为生成应用创建一个独立 Vercel Deployment，也不需要为维持预览而让构建沙盒一直运行。

本地开发是另一条适配路径：使用 macOS sandbox-exec 构建并启动受控 Vite 预览进程，失效后由恢复流程重建。完整本地沙盒尚未适配 Windows / Linux。

### 1.6 两层持久化与版本一致性

| 数据 | 保存位置 | 当前保证与边界 |
| --- | --- | --- |
| 项目、聊天、源码与成功版本 | Supabase Postgres | 登录后可以恢复；各版本关联同一项目，回滚保存为新版本 |
| 成功构建产物 | Supabase 私有 Storage | 与成功执行记录及版本关联，不依赖临时沙盒目录 |
| 生成应用中的任务、账目或习惯 | 应用独立 Origin 的 localStorage | 当前浏览器刷新可保留；不承诺跨设备同步或多用户共享 |

云端写入使用项目租约、版本校验和事务化快照，避免旧任务覆盖较新的结果。文件路径与消息顺序有对应约束。仍待完善的是多表的一致性读取，以及失败执行信息的完整持久化。

**代码回滚不等于业务数据回滚。** 应用数据并没有按每个代码版本保存独立快照；如果后续改动改变了数据结构，需要考虑兼容和迁移，不能保证任意生成代码都天然保留旧数据。

### 1.7 权限与不可信代码边界

- 项目接口验证服务端会话和项目归属，不信任前端传入的用户身份；数据库通过 RLS 限定用户数据范围。
- 模型只能生成受控路径内的文件，不能任意安装依赖或运行命令；构建过程限制文件访问、联网、资源与执行时间。
- 生成页面使用项目独立 Origin 与 sandboxed iframe，避免直接继承宿主登录环境；只有隔离 Origin 下才开放所需的同源存储能力。
- 云端产物为私有存储，预览通过短期签名授权访问，并限制页面可使用的资源通道。

这些是当前 Demo 的工程边界，不代表已经完成商业规模下的全部安全、滥用防护或配额设计。

### 1.8 开发过程中的代表性问题与修正

| 问题 | 判断与处理 | 工程意义 |
| --- | --- | --- |
| 生成文件使用独立类型文件时被拒绝 | 补齐受控类型文件路径，同时保留路径越界检查与旧文件清理 | 文件合同既要限制风险，也要覆盖合理的工程结构 |
| 应用在 iframe 中无法正常使用本地存储 | 区分宿主与预览 Origin，在隔离前提下配置 iframe 权限 | 页面能显示不等于交互和数据持久化可用 |
| 线上 iframe 遇到平台部署保护拦截 | 核验预览域名的归属与平台配置，而不是关闭保护绕过问题 | 构建成功、地址可访问和浏览器能嵌入是不同验收条件 |
| 记账应用功能正常，但自动化因缺少测试标识失败 | 改为严格的语义定位与金额断言，不读取整个页面兜底 | 先区分产品缺陷与定位器问题，不用弱化断言换取通过 |
| 真实项目封面增加首次等待与沙盒用量 | 验证截图能力后，将首页收敛为静态统一卡面 | 为当前演示目标控制复杂度，不把可选展示能力变成运行依赖 |

### 2.2 已执行的验证

下面是开发过程中取得的验证结果，不表示本次编写文档又重跑了全部测试，也不保证任意自然语言需求都能得到正确应用。

| 场景 | 验证内容与结果 |
| --- | --- |
| 同项目多轮修改 | 真实模型生成 Todo，再增加深色模式和优先级；验证版本连续变化、项目 ID 不变、刷新和重新登录后恢复，并拒绝第二账号访问。该链路不单独覆盖主题按钮、优先级控件的所有交互组合 |
| 三个代表应用 | 任务管理、习惯打卡、个人记账的真实交互和刷新持久化已分两轮取得通过结果，不把它写成同一批一次性全通过 |
| 版本回滚 | 本地真实数据库、模型、沙盒与 iframe 回滚链路已验证；不把本地结果等同于所有线上回滚场景已完成验收 |
| 邮箱确认 | 一个此前未注册、非 Supabase 团队成员的新 Gmail 实际收信；确认后自动登录，退出后密码登录成功，没有管理员确认代替收信 |
| 统一封面 | 正式站桌面和 320px 移动视口两项通过；刷新后无截图请求，正常流程无 console/pageerror 和 HTTP 4xx/5xx |

测试分层包括模块测试、API/持久化集成和 Playwright 浏览器验收。实际 API 调用、数据库写入与沙盒恢复需要专门的真实测试；UI 契约样本和模块 Mock 只用于验证各自层级，不能冒充真实生成结果。

开发采用增量验证：先复现问题或编写失败测试，修复后验证受影响范围，在里程碑执行构建或端到端回归；代码审查作为独立环节处理并发、边界和隔离问题。

### 2.3 未做与当前局限

- 没有多模型赛马、模型评分择优或多智能体自由对话框架。
- 没有运行中消息排队、持久化 SSE 回放和可靠后台任务续跑体系。
- 没有点选元素编辑、Remix、完整可视化样式面板或独立应用发布。
- Google 一键登录、分享发布暂缓；使用 Gmail 注册仍是邮箱密码流程。
- 生成应用以受控前端工程为主，不提供它自己的服务端、托管业务数据库或任意外部 API 能力。
- 构建与已测用例通过不等于模型生成的所有业务逻辑都正确，也不能保证任意修改都保持数据结构兼容。
- 用户规模、费用监控、邮件长期投递、真实移动设备与大陆多运营商网络仍需继续验证。

## 3. 继续投入时的优化计划

原则是先提高当前闭环的可靠性，再扩展生成质量和产品能力；以下均为计划，不计入当前已实现功能。

| 阶段 | 事项 | 预期价值 |
| --- | --- | --- |
| P0：可靠性 | 完整保存失败消息、阶段事件和修复结果，明确中断与可重试状态 | 用户刷新或返回项目后仍能理解失败原因 |
| P0：一致性 | 将多表读取收敛为一致快照，补充并发修改与版本冲突验收 | 避免读取到不同时间点的项目状态 |
| P0：资源控制 | 完善应用级配额、滥用防护、用量监控与明确的超时反馈 | 支撑持续公开演示，控制模型与沙盒消耗 |
| P1：清理与观测 | 安全回收失败任务遗留产物，完善结构化日志与错误分类 | 降低运维负担，不误删成功版本 |
| P1：质量闭环 | 对成功生成的应用加入受控运行时与业务交互检查 | 从“构建能通过”进一步走向“关键功能正确” |
| P1：体验 | 长对话、真实手机、缩放、不同网络和邮箱投递验收 | 减少环境变化导致的体验差异 |
| P2：产品扩展 | 在明确需求后考虑 Google 登录、分享发布、版本差异查看 | 扩展使用场景，不提前承诺交付 |
| P2：数据能力 | 评估受控后端与多用户业务数据方案 | 需要额外的权限、隔离、配额和迁移设计，不能直接放开模型任意执行 |

## 4. 建议评审路径

1. 先从在线站点体验“生成 → 预览中真实操作 → 原项目继续修改”。
2. 查看源码与版本历史，刷新或重新登录后恢复同一个项目。
3. 从生成 API 阅读 Agent、Sandbox 和持久化链路，重点检查“保存成功”和“预览就绪”是否被正确区分。
4. 对照本说明的功能边界与测试，区分真实集成结果、UI 契约样本和待完成事项。

| 评审关注点 | 可观察的证据 |
| --- | --- |
| 完成度 | 线上可访问，认证、生成、修改、保存和预览组成可体验闭环 |
| 工程思维 | 固定依赖、有限修复、非破坏性回滚、构建/预览分离、租约与版本防护 |
| 用户体验 | 阶段状态、错误反馈、恢复入口、源码查看、响应式布局与统一项目卡面 |
| 验证可信度 | 真实模型/数据库/沙盒的测试与 UI 样本明确分开，失败原因和未测范围不隐藏 |
| 可维护性 | 模型、文件、Sandbox、持久化和预览分别有代码入口，文档记录边界与后续工作 |

## 附录：主要接口与数据实体

### A. 主要接口

| 接口 | 用途 |
| --- | --- |
| `POST /api/generate` | 创建或修改项目，返回 SSE 执行事件 |
| `GET /api/projects` | 当前用户的项目列表 |
| `GET /api/projects/[projectId]` | 项目详情、已保存源码和对话状态 |
| `POST /api/projects/[projectId]/resume` | 恢复当前项目与预览 |
| `POST /api/projects/[projectId]/restore` | 恢复历史代码并保存为新版本 |
| `GET /api/projects/[projectId]/preview-status` | 查询预览状态 |
| `GET /api/preview/[projectId]/` | 通过授权读取预览内容 |
| `/auth/callback`、`POST /auth/logout` | 认证回调与退出 |

宿主项目接口使用服务端会话和项目权限校验。线上预览访问采用独立的短期签名授权；本地预览由网关转发受控 Vite 进程，两者不能简单等同于宿主页面的登录请求。

### B. 主要数据实体

| 实体 | 内容 |
| --- | --- |
| `projects` | 用户归属、项目名称、当前成功版本与时间信息 |
| `messages` | 项目对话及消息顺序 |
| `project_files` | 当前保存的源码，项目内文件路径唯一 |
| `project_versions` | 可恢复的成功源码快照，项目内版本号唯一 |
| `agent_runs` | 与成功版本关联的执行结果；失败记录完整持久化仍待补齐 |
| `project_leases` | 云端同项目写入的租约与版本防护 |
| 私有 Storage | 版本对应的静态构建产物，不承担生成应用业务数据库的角色 |
