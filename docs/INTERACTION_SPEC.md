# Atoms Demo MVP：交互规格

## 1. 文档目的

本文档只规格化两条核心交互：

1. 用户首次提交需求并获得第一个可用应用。
2. 用户在同一项目中通过多轮对话修改应用并获得新版本。

本文档不描述登录、计费、连接器、发布细节、GitHub、代码编辑器或可视化编辑器，也不包含实现代码。

## 2. 证据与表述规则

- **观察：** 来自 REA 页面检查、截图或有序无障碍节点。
- **推测：** 有证据支持但未直接执行验证。
- **实现建议：** Atoms Demo MVP 应采用的交互要求，不代表 Atoms 内部实现。
- **未知：** 本轮没有直接证据，不作为必经流程。

REA 只做被动观察。打开页面、关闭临时浮层和提交一次后续修改由外部 CDP 完成，并与 REA Evidence 分开归因。

## 3. 核心对象

| 对象 | 作用 | 已观察表现 |
| --- | --- | --- |
| 项目 | 容纳需求、对话、预览和版本 | 项目名固定显示在工作区顶部 |
| 用户消息 | 描述首次需求或后续修改 | 后续请求以浅灰圆角气泡追加 |
| Agent | 解释计划并执行生成/修改 | 显示头像、姓名、角色和思考状态 |
| 工具步骤 | 公开具体执行过程 | 文件读取/写入、终端、质量检查、可视化检查 |
| App Viewer | 持续呈现可交互结果 | 处理中保留旧版本，完成后刷新 |
| 版本 | 保存一次完成结果 | 版本 1、版本 2 卡片及“恢复到此版本”入口 |
| 后续输入框 | 发起下一轮修改 | 本轮捕获状态中位于对话栏底部 |

本文档首次出现时，`Agent` 指智能体，`App Viewer` 指应用查看器。

## 4. 首次生成应用流程

主要证据：`ev_24a0b2007276e89039e9792679e9785180dcc3b176fe0a1f39e39fa16d7415e8`、`ev_512a773e3ca0d0ddc62c7ba7bbcf1ee079595c1630319962dee16c251dc3ece5`。

### 4.1 已观察的需求

本轮既有项目的首次需求为：

> 个人主页生成器：输入姓名 / 职业 / 技能 / 联系方式 → 生成排版精良的个人主页。

需求旁出现“让智能体团队实现”。

### 4.2 根据既有时间线重建的顺序

以下顺序来自一个已经完成的项目时间线及其有序无障碍节点，不是对首次生成全过程的实时录制。单个步骤文本属于直接观察；步骤之间的状态归纳属于分析模型。

#### 状态 A：需求进入项目

**观察：** 需求作为对话内容存在于项目工作区中；右侧为 App Viewer。

**未知：** 本轮没有直接捕获从首页点击“开始”到工作区创建完成之间的所有瞬间状态，因此不确认是否必然出现独立积分确认、需求规划审批或项目命名步骤。

#### 状态 B：Agent 启动

**观察：**

- Agent 显示 `I’m getting started.`。
- 随后用一句自然语言复述实现方向：先初始化模板，再实现表单输入和实时预览。
- 在工具执行前，界面会先展示 Agent 对任务的理解。

#### 状态 C：透明执行

**观察：** Agent 在时间线中交替展示意图说明和工具步骤。本次顺序包括：

1. 阅读模板说明。
2. 读取 `README.md`、`App.tsx` 和 Tailwind 配置。
3. 写入 `DESIGN.md`。
4. 实现数据模型与 HTML 生成逻辑。
5. 写入 `profile.ts`、`index.css`、`ThemeTabs.tsx` 等文件。
6. 在终端运行 lint/build。
7. 进行可视化检查。
8. 更新进度并结束。

工具组允许折叠，并显示“显示 N 个更多”；用户可以理解当前阶段，而不必默认展开全部技术细节。

#### 状态 D：验证

**观察：**

- Agent 明确报告 lint 和生产构建通过。
- 随后执行可视化检查，并报告界面与设计规范一致。
- 验证不是隐藏的后台动作，而是对话时间线中的可见步骤。

#### 状态 E：交付总结

**观察：** Agent 给出：

- 已实现的核心流程。
- 预览和主题能力。
- 导出能力。
- 质量验证结果。
- 发布或继续扩展的建议。

同时，右侧 App Viewer 提供可交互应用，不需要离开对话页。

#### 状态 F：版本完成

**观察：**

- 出现“完成个人主页生成器首版”。
- 新增“版本 1”卡片。
- 底部后续输入框保持可编辑，允许继续对话。

### 4.3 Demo 首次生成状态机

以下状态机是根据观察结果整理的**实现建议**，不是对 Atoms 内部状态名称的观察。

| 状态 | 进入条件 | 用户可见反馈 | 退出条件 |
| --- | --- | --- | --- |
| `submitted` | 需求已提交 | 需求出现在时间线 | Agent 接受任务 |
| `starting` | Agent 开始处理 | 启动提示和实现方向 | 首个工具步骤开始 |
| `working` | 正在生成 | 意图说明、工具步骤、折叠详情 | 进入验证 |
| `validating` | 主体实现完成 | 终端检查、质量验证、可视化检查 | 验证成功或失败 |
| `summarizing` | 验证完成 | 功能清单、质量结果、下一步建议 | 开始版本封装 |
| `versioning` | 结果准备完成 | 版本正在生成或即将出现 | 版本卡可用 |
| `ready_v1` | 版本创建完成 | 可交互预览、版本卡、后续输入框 | 用户提交下一轮修改 |

### 4.4 MVP 首次生成要求

以下为**实现建议**：

- 提交后立即把用户需求写入时间线，避免无反馈等待。
- Agent 必须先复述理解，再执行工具步骤。
- 至少公开“规划/实现/验证/交付”四类阶段；不要求伪造过细的技术日志。
- 工具步骤支持默认折叠，避免长时间线淹没重要信息。
- 将“预览可用”和“流程完成”分开：`hasPreview=true` 是正交布尔标记，不是互斥主状态；版本卡创建成功后，首次生成主状态才进入 `ready_v1`。
- 版本创建完成前，发布按钮保持不可用。
- 流程完成时必须生成版本卡，并保留后续输入入口。

### 4.5 Demo 从首页到工作区的实现选择

以下内容是为补足原产品未知区间而定义的 **Demo 实现建议**：

1. 首页提示词为空时，“开始”按钮不可提交；输入非空文本后按钮可用。
2. 点击“开始”后立即创建一个项目，并把原始提示词作为时间线第一条用户消息。
3. 登录不属于本规格范围；如果宿主要求登录，应在登录完成后携带原提示词继续，不要求用户重新输入。
4. 项目创建后直接进入 Agent 工作区，不增加独立的积分确认或需求审批页面。
5. 首次生成开始但尚无稳定 artifact 时，Viewer 显示明确的空状态/构建中状态；首个可交互 artifact 到达后切换为预览。
6. 首个可交互 artifact 到达后设置 `hasPreview=true`；只有版本卡创建成功才进入 `ready_v1`，并恢复发布能力。

这些选择用于让 Demo 可独立实现，不应写成 Atoms 已观察事实。

## 5. 多轮对话修改流程

本轮直接提交并观察的修改请求为：

> 把成品页的朱红强调色改为深蓝色，其他布局和内容保持不变。

运行态证据：`ev_48bdf2a20a2b8ce8cb58afa5e53d726b00c98085c6f6b7d92415f06eb69299e2`、`ev_b6a3dfc242a9625158ef805cc9e09115b23202c578ebef8c945668ec12e6e7b0`。

终态证据：`ev_60bd12ac7f454ac530cb0cb8a4210fbd1048bcb5abb0cca8799417f1920b18ee`、`ev_65743bd1389adb027a8a83bdc43c65c93a3f4769c7caaed7c19c5577af1ec239`。

### 5.1 提交后立即变化

**观察：**

- 新请求以浅灰消息气泡追加在版本 1 之后。
- 不创建新页面，也不离开当前项目。
- 出现 Agent 头像、`Alex｜工程师` 和 `Alex 正在思考`。
- 输入框右下的发送箭头切换为黑色停止方块。
- 顶栏出现“跟随智能体”。
- “发布”按钮变为淡蓝禁用状态。
- App Viewer 保留上一个稳定版本，没有切换为整页 loading。

### 5.2 Agent 先确认修改边界

**观察：** Agent 首先说明：

> 我先确认成品页的强调色定义，只修改颜色，保持布局、内容和编辑工作台不变。

随后读取 `profile.ts`，并明确将朱红色改为深蓝色 `#173B65`，预览与导出同步生效。

**实现建议：** 对局部修改，Agent 应在执行前重述“改什么”和“不改什么”，让用户能够发现范围漂移。

### 5.3 修改与验证

**观察：** 状态依次为：

1. `读取文件 profile.ts`。
2. 说明颜色替换方案。
3. “颜色已替换，我现在运行代码检查和生产构建。”
4. “代码检查与构建通过，现在确认成品页显示深蓝强调色且布局内容保持原样。”
5. 可视化检查。
6. “界面检查确认修改符合要求，我记录本次完成状态。”
7. 给出最终变更总结。

本轮捕获到的多个运行状态中，App Viewer 都保留版本 1；新版本封装完成后才观察到版本 2 预览。

### 5.4 版本封装

**观察：**

- Agent 已宣布修改完成后，宿主进入“正在构建版本”。
- 版本封装完成后出现“版本 2”卡片，标题为“成品页强调色改为深蓝”。
- App Viewer 中的方形标记和横向强调线从朱红更新为深蓝，其他可见排版保持一致。
- “发布”按钮恢复可用。
- 页面结构中出现“恢复到此版本”入口。

**推测：** “恢复到此版本”很可能执行版本回滚，但本轮未点击，因此不能断言回滚后的确认、数据处理或新版本生成方式。

### 5.5 多轮修改状态机

以下状态机是 **Demo 实现建议**。`isReady=true` 适用于 `ready_v1`、`ready_v2` 及后续完成版本；只有这些状态允许发布。

| 状态 | 触发 | UI 反馈 | 预览策略 |
| --- | --- | --- | --- |
| `ready_v1` | 版本 1 已完成 | 发送可用、发布可用 | 显示版本 1 |
| `change_submitted` | 用户发送修改 | 追加消息气泡 | 继续显示版本 1 |
| `change_thinking` | Agent 接受修改 | Agent 角色、思考状态、停止按钮、跟随入口 | 继续显示版本 1 |
| `change_working` | Agent 执行工具 | 范围确认、文件操作和进度文本 | 继续显示版本 1 |
| `change_validating` | 修改代码完成 | 构建检查、可视化检查 | 继续显示版本 1 |
| `change_summarizing` | 检查通过 | 变更总结 | 继续显示版本 1 |
| `change_versioning` | 宿主保存新结果 | “正在构建版本”，发布保持禁用 | 继续显示版本 1 |
| `ready_v2` | 版本 2 完成 | 新版本卡、发送恢复、发布恢复 | 原子切换为版本 2 |

### 5.6 MVP 多轮修改要求

以下为**实现建议**：

- 所有修改继续写入同一项目时间线，不为每轮创建新项目。
- 新消息提交后必须立即可见。
- 运行时将发送按钮切换为停止按钮；停止入口必须有可访问名称。
- 运行中禁用发布，避免发布半成品。
- 修改期间继续显示最后一个稳定预览。
- Agent 必须展示范围确认、执行进度、验证结果和最终摘要。
- 每次成功修改创建一个不可混淆的新版本卡。
- 预览只在新版本准备完成后原子切换；进入 `ready_v2` 前始终显示版本 1。
- 版本卡至少显示版本号和简短变更标题。

## 6. 共享交互规则

### 6.1 进度透明度

**观察：** 首次生成和后续修改都把 Agent 的自然语言解释与工具步骤交错展示。

**实现建议：**

- 不使用单一无限旋转 loading 代替全过程。
- 每个阶段提供一句人类可理解的说明。
- 技术细节可以折叠，但阶段和失败必须可见。

### 6.2 预览连续性

**观察：** 本轮多轮修改的多个捕获状态中，旧预览保持可用；新版本完成后观察到预览更新。

**实现建议：** Viewer 维护 `stableArtifact` 和 `pendingArtifact` 两种状态，只有后者通过验证并保存为版本后才替换当前预览。这里是 Demo 架构建议，不是对 Atoms 内部实现的判断。

### 6.3 发布控制

**观察：** 空闲时发布可用；Agent 运行时发布禁用；版本完成后恢复。

**实现建议：** 只有满足 `isReady=true` 的完成版本状态（例如 `ready_v1`、`ready_v2`）允许发布。生成、验证、保存版本或错误处理尚未结算时禁止发布；失败结算并回到上一稳定 `ready_vN` 后，恢复对该稳定版本的发布能力。

### 6.4 停止与恢复

**观察：** 运行时出现停止按钮及“若需停止所有任务请点击此处”的可访问文本。

**未知：** 本轮没有点击停止按钮，因此不确认取消是否立即终止、是否保留部分结果、是否扣除积分或如何恢复。

### 6.5 版本恢复

**观察：** 版本结构中存在“恢复到此版本”。

**未知：** 未执行恢复，不确认其是否覆盖当前版本、创建新版本、是否需要确认，或是否影响生成应用数据。

## 7. 异常与边界状态

本轮没有直接触发以下状态，因此它们不是 Atoms 已观察事实，也不属于本轮四项调研的主要验收场景：

- Agent 请求失败。
- 网络断开。
- 用户停止任务。
- 代码检查失败。
- Viewer 加载失败。
- 版本保存失败。

**Demo 最小实现建议：**

- 如果已有稳定版本，失败或停止后保留该版本及其预览，不创建新版本；恢复输入框，并允许继续提交请求。
- 如果首次生成尚无稳定版本，显示可重试错误空状态；发布保持禁用。
- 如果后续修改失败，先结算失败并回到上一稳定 `ready_vN`；随后恢复对该稳定版本的发布能力，但不得发布失败中的 pending artifact。
- 停止任务后显示“已停止”，恢复普通发送按钮；停止操作的服务端取消语义不在本规格中定义。
- Viewer 或版本保存失败时在对话栏展示错误和重试入口，不清空历史版本。
- “恢复到此版本”的实际回滚流程不纳入本轮 MVP 验收；只要求版本入口可见。

## 8. 本轮明确未知项

- 首页首次提交后是否一定要求登录，以及完整跳转顺序。
- 首次生成前是否一定存在需求规划审批或积分确认。
- 首次生成中 Viewer 从空白、骨架到首个可交互预览的精确时机。
- 停止按钮的实际取消语义。
- “跟随智能体”的滚动/聚焦规则。
- “恢复到此版本”的完整行为。
- 宿主工作区的移动端栏位切换方式。

这些未知项不得在实现说明中伪装为 Atoms 已观察事实。

## 9. 端到端验收场景

### 场景 A：首次生成

1. 首页提示词为空时不可提交；输入有效文本后“开始”可用。
2. 用户提交一句应用需求。
3. 时间线立即显示用户需求。
4. Agent 复述理解并进入可见执行阶段。
5. 用户能看到规划说明、实现步骤、验证/可视化检查和交付总结四类反馈。
6. Viewer 出现可交互应用，设置 `hasPreview=true`。
7. 系统创建版本 1 后进入 `ready_v1`。
8. 后续输入框和发布恢复可用。

### 场景 B：局部修改

1. 用户在版本 1 下方提交局部修改。
2. 新消息立即追加；发送按钮变为停止按钮。
3. Agent 明确“改什么”和“不改什么”。
4. 运行中发布禁用，Viewer 保持版本 1。
5. Agent 显示修改、构建和视觉验证过程。
6. 系统显示正在构建版本。
7. 创建版本 2，并刷新 Viewer。
8. 发布和普通发送恢复可用。
9. 版本区域保留版本 1 与版本 2，并提供恢复入口。

## 10. 调研结论

Atoms 的核心交互不是“输入提示词后等待一个结果”，而是同一工作区内持续存在的三部分闭环：

1. 对话时间线公开 Agent 的理解、工具和验证过程。
2. 本轮多轮修改的捕获状态中，App Viewer 持续提供当前稳定应用。
3. 每次成功生成或修改都沉淀为可识别版本，并允许继续对话。

对 Atoms Demo MVP，最重要的复刻点是状态连续性与可见反馈，而不是扩展更多非核心入口。
