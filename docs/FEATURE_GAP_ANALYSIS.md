# Atoms 项目页功能缺口分析

> 目标页面：`https://atoms.dev/zh/chat/a490173206ba4961b73447f50c0d6535`  
> 调研时间：2026-10-13  
> 范围决定：第一层必须保存项目源码、对话消息、执行记录、版本元数据与可预览产物；第二层也尽量对齐 Atoms 的独立预览环境，让明确要求持久化的生成应用能够在刷新后保留业务数据。

## 2. 已观察到的目标页能力

以下均为直接观察：

1. 项目拥有稳定的 `/zh/chat/{projectId}` 地址；直接打开既有地址后，页面显示原项目名、两轮对话、版本 1、版本 2 和当前预览。
2. “历史记录”区域列出两个版本，包含变更标题、时间、版本号和“恢复”入口。
3. 每轮 Agent 结果包含处理步数、交付总结、版本卡和“克隆”入口。
4. 顶栏存在“分享”和“发布”；运行态证据中发布会禁用，版本完成后恢复。
5. App Viewer 存在重新加载、首页、移动预览、在新标签页打开和控制台入口。
6. Viewer 中存在“选择元素、修改文本、主题”设计工具条。
7. 多轮修改继续发生在同一个项目中；修改完成前保留旧预览，完成后出现新版本。

以下为 Playwright/CDP 的直接运行观察，不归因于 REA：

1. 成品运行在独立的 `https://…app.atoms.dev` Origin，而不是 `atoms.dev` 主站同源。
2. 成品 frame 可以访问 `localStorage`，当时有 2 个非业务键；IndexedDB 数据库数量为 0。
3. 当前“个人主页生成器”没有保存临时表单修改：姓名字段改成测试标记后，Viewer 重载恢复为版本默认值。

因此可确认的是：Atoms 为成品提供了独立、可使用浏览器存储的 Origin；不能据此声称每个 Atoms 生成应用都会自动保存业务数据，是否保存仍取决于应用实现。

## 4. 第一层持久化的准确实现范围

### 必须保存

- `projectId`、项目名、创建/更新时间和当前版本号。
- 每个版本的完整源码或可重建快照、文件清单和构建结果。
- 用户消息、Agent 回复、每轮状态、执行事件、错误和自动修复次数。
- 已通过构建的静态预览产物，或能够在冷启动时确定性恢复该产物的引用。
- 当前稳定版本指针；版本恢复后必须原子切换源码、预览和后续修改基线。

### 必须支持的用户结果

- 刷新或重新打开项目 URL 后，回到同一个工作区，而不是首页。
- 能看到原对话、执行结果和版本历史。
- 能加载最后一个成功版本的真实预览，并继续修改同一个项目。
- 失败轮次不能覆盖最后一个成功版本。

### 第一层不包含

- 为生成应用自动创建数据库、用户系统或任意后端接口。
- 让不可信生成代码直接访问宿主 Cookie、Local Storage 或主站同源权限。

## 5. 第二层持久化的对齐范围

### 必须达到的用户结果

- 当生成需求明确写出“刷新后保留数据”时，任务、账目、习惯及完成状态必须在 Viewer 重载后保留。
- 刷新整个宿主页并恢复同一个项目和最新版本后，生成应用业务数据仍可读取。
- 持久化失败不得导致 React 应用白屏；读取失败应回退到安全初始值并报告运行错误。

### 与 Atoms 对齐的安全边界

- 生成应用必须运行在与主站隔离的预览 Origin，或通过受限父子页面存储桥获得等价能力。
- 不应在当前同源 `/api/preview/...` iframe 上直接增加 `allow-same-origin`；这样会把不可信生成代码提升到宿主 Origin 权限。
- 存储按项目隔离，并设置容量、结构和写入频率限制；不能读取其他项目或宿主认证数据。

### 不作过度推断

- 当前 Atoms 样例的表单改动在 Viewer 重载后会复位，所以“不要求持久化”的普通应用可以保持临时状态。
- 观察到 `localStorage` 可用不等于 Atoms 自动为所有应用同步数据，也不能证明跨设备或跨版本同步。

## 6. 建议执行顺序

1. **先补云端项目存储和静态预览产物存储。** 现有本地 JSON、源码目录和版本快照可以继续作为开发适配器，但线上必须换成持久存储。
2. **增加项目路由与恢复加载。** 让 `/projects/{id}` 或等价路由读取项目、消息、执行记录、版本和当前预览。
3. **实现版本历史与恢复。** 复用已经存在的 `.atoms/versions/{n}` 语义，增加读取、恢复、重新构建/选取产物及原子切换。
4. **补第二层安全存储能力。** 优先采用独立预览 Origin；如果免费部署条件无法提供项目级 Origin，则使用固定 Runtime 与受限 `postMessage` 存储桥。
5. **再补发布/分享和访问控制。** 对 1–2 个用户可采用最小邀请登录或带所有权校验的私有项目，不需要完整商业账号体系。
6. **最后处理体验增强。** 真实取消、控制台、克隆和设计工具不应抢占持久化与恢复闭环。

## 7. 结论

当前 Demo 的“自然语言生成、真实构建、iframe 交互、多轮增量修改、源码与执行记录落盘”核心已经成立。第一层仍有四个 P0 缺口：**线上持久存储、稳定项目 URL 恢复、冷启动预览恢复、版本历史与恢复**。第二层则缺少 Atoms 已观察到的“独立预览 Origin + 可用浏览器存储”平台能力；三个代表性用例现已把刷新后的业务数据保留重新纳入验收，但不强制具体存储 API。分享、发布、取消、克隆和设计工具继续按优先级后补。
